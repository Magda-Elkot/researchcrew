## 2.1 uv: the package manager

**What:** `uv` installs Python packages (like `pip`, but much faster) and manages the project.

**Two important files:**

| File | Simple meaning | Example |
|---|---|---|
| `pyproject.toml` | The **shopping list**: what we need | `crewai>=1.15.41` (version 1.15.41 or newer) |
| `uv.lock` | The **receipt**: exactly what we got | `crewai==1.15.41` and all 204 packages with exact versions |

**Why a lockfile?** You, the CI machine and Docker all install **the same** versions,
so "it works on my machine but not on yours" doesn't happen.

**`.venv`** = the project's private folder of installed packages (2.4 GB).
`uv run <command>` runs a command using `.venv`, so you never need to "activate" it.

## 2.2 Dependency groups

We split packages into groups, because each container needs different things:

| Group | Used by | Main packages |
|---|---|---|
| (shared) | everything | pydantic, pydantic-settings |
| `api` | the API container | crewai, fastapi, litellm, langfuse, mcp |
| `docs` | the docs-mcp container | sentence-transformers, torch (CPU), pymupdf, qdrant-client |
| `frontend` | the web page | streamlit |
| `dev` | only your laptop and CI | pytest, ruff, mypy |

So the docs-mcp image doesn't carry crewai, and the api image doesn't carry torch.

## 2.3 The version conflict we solved (a good interview story!)

1. We asked for crewai, mcp and pydantic. uv **silently** picked **old** crewai 1.6.1.
2. We noticed it with `uv tree --outdated` (the newest was 1.15.41).
3. We asked for the new version, and uv explained why it couldn't:
   new crewai needs **mcp < 2** and **pydantic < 2.13**, but we had asked for newer versions of both.
4. **Decision:** use the newest crewai and accept mcp 1.30 and pydantic 2.12 (DECISIONS #20).

**Lesson:** when a resolver "succeeds", check *what* it chose. It may have gone backwards to satisfy everyone.

## 2.4 CPU-only PyTorch

Torch from the normal index includes NVIDIA GPU libraries (about 2–3 GB) that we don't need,
because our embedding model runs on the CPU.
We told uv to take **only torch** from PyTorch's special CPU index. The result: `torch 2.15.0+cpu`.

## 2.5 Configuration: `app/config.py`

**Rule:** no passwords, URLs or model names written inside the code. Everything comes from
**environment variables** (or the `.env` file).

```
.env file:   QDRANT_URL=http://localhost:6333
                    │
                    ▼
Settings class:  settings.qdrant_url  →  "http://localhost:6333"  (checked: must be a string)
```

- `Settings` is a Pydantic class, so wrong values give a clear error at startup.
- `get_settings()` creates the settings **once** and reuses them (a cache).
- `require("GROQ_API_KEY")` stops the program with a clear message:
  `Missing required environment variable: GROQ_API_KEY`.
- API keys are **optional when the code is imported**, so tests and CI work without secrets.
  They are checked when the app **starts**.
- `.env` holds **your real values** and is never committed. `.env.example` is a template with fake values and is committed.

## 2.6 Logging: `app/log.py`

Every log line is **JSON**, so machines can search it:

```json
{"timestamp": "2026-11-13T17:15:09+00:00", "level": "INFO", "logger": "app.cli", "message": "..."}
```

**Hiding secrets (redaction)**, done in two ways:
1. **By field name:** a field called `groq_api_key`, `password` or `authorization` becomes `***`.
2. **By value:** if the real key text appears anywhere in a message, it becomes `***`.
   URLs like `?apiKey=abc` become `?apiKey=***`.

But `prompt_tokens` is **kept**: it is a count, not a secret, and we need it to measure cost.

**Why `log.py` and not `logging.py`?** Python already has a module called `logging`. Same name means confusion.

## 2.7 Data models: `app/schemas.py`

A **schema** is a strict form that data must fill correctly. Pydantic checks it automatically.

| Model | Means | Example rule |
|---|---|---|
| `ResearchPlan` | The Planner's output | Must have **3 to 6** sub-questions |
| `EvidenceItem` | One fact with its source | `source_type` must be `"web"` or `"doc"` |
| `Finding` | A conclusion | `confidence` must be high, medium or low |
| `Report` | The final report | Title, sections, citations `[n]` |
| `ReviewResult` | The Reviewer's verdict | `approved: true/false` |
| `ResearchRequest` | What the user sends | The question can't be empty; max 2000 characters |
| `ProgressEvent` | A live progress message | `type` must be one of 7 known events |

If an AI agent returns 7 sub-questions, Pydantic rejects it. We don't have to check by hand.

## 2.8 The placeholder API: `app/api/main.py`

**FastAPI** = a Python library for building web APIs.

| Endpoint | Returns | Used for |
|---|---|---|
| `GET /health` | `{"status": "ok", "version": "0.1.0"}` | "Is the server alive?" Docker checks this. |
| `GET /metrics` | Request counts and response times | **Prometheus** (a monitoring tool) reads this. |

**Lifespan** = code that runs when the server starts and stops. Ours runs `require()` there.

**Metrics label trick:** we record `/research/{id}`, not `/research/abc123`.
Otherwise every new job id would create a new metric, and memory would grow forever.

## 2.9 Docker

**Docker** packs the app and everything it needs into an **image**. Running an image gives a **container**.

**Our api image (`docker/api.Dockerfile`), multi-stage:**
```
Stage 1 "builder":  install packages with uv  (has build tools, big)
                         │ copy only the finished .venv
                         ▼
Stage 2 "runtime":  python + .venv + our code  (smaller, cleaner)
```
- It runs as a **non-root user** `app`. If someone hacks it, they don't get admin rights.
- **HEALTHCHECK:** Docker calls `/health` every 15 s to know whether the container is healthy.
- **Layer caching:** we copy `pyproject.toml` and `uv.lock` first, then install, then copy the code.
  If only the code changes, Docker reuses the slow install step.

**`docker-compose.yml`** starts **two containers together**:
- `qdrant`: the vector database (pinned to `v1.20.1`).
- `api`: waits until Qdrant is healthy (`depends_on`).

On your machine, port 6333 was already used by another project, so our Qdrant uses **6335**
(set in your `.env`).

## 2.10 Code quality tools

| Tool | What it does | Example |
|---|---|---|
| **ruff check** | Finds style problems and simple bugs | Unsorted imports (`I001`), a line too long (`E501`) |
| **ruff format** | Formats code automatically | Fixes spaces and line breaks |
| **mypy** | Checks **types** without running the code | "this function expects str, you gave int" |
| **pytest** | Runs our tests | 55 tests in Phase 1 |

**Tests never call real AI or paid APIs.** We use fakes ("mocks"). Fast, free, and no network needed.

## 2.11 Makefile: shortcuts

`make check` = `ruff check` + `ruff format --check` + `mypy` + `pytest`, all in one command.

## 2.12 CI: GitHub Actions (`.github/workflows/ci.yml`)

**CI = Continuous Integration.** On every push, GitHub runs our checks on a clean computer:
1. Job `lint-test`: install everything, then ruff, mypy, pytest.
2. Job `docker`: check that the image still builds.

A green check ✅ on GitHub means "the code in this commit works".
